아키텍처 기준배포 단위 3개정 2 · 인덱스 전략 추가

날짜는 컬럼이 아니라
이력 행으로 넣는다

임직원 서비스가 입퇴사·발령 날짜를 갖는 건 맞다. 다만 발효일과 등록일 두 축을 함께 갖지 않으면 소급 발령을 표현할 수 없고, 급여 재계산 판단이 불가능해진다. 이 문서는 서비스 세 개의 배치 근거와 날짜 설계 기준을 정리한 것이다.

결론

배포 단위는 셋, 인증은 별도 인프라

근태확정 → 급여 → 4대보험 체인은 코어 한 배포 단위 안에 있다. 이 셋이 한 커밋에 묶인다는 게 사가가 필요 없는 이유이고, 임직원이 밖으로 나가도 이 성질은 변하지 않는다. 코어는 마감 시점에 임직원 정보를 스냅샷으로 확보하고, 그 이후 계산은 전부 DB-2 안에서 끝난다.

근거 · 분리 판단

소비자가 급여 체인 밖에 있으면 분리한다

임직원 마스터를 코어에 두느냐 빼느냐는 누가 읽는가로 갈린다. 소비자가 급여 체인 넷뿐이라면 코어에 두는 게 맞다. 팩스·메일·알림처럼 급여와 무관한 서비스들이 함께 읽는다면 분리가 맞다.

다만 분리했으니 소비 방식을 두 갈래로 나눠야 한다. 같은 방식으로 서비스하면 한쪽이 반드시 깨진다.

참조형 · 팩스 메일 알림계산형 · 급여 4대보험
필요한 것이름, 이메일, 현재 부서기준일 시점의 재직·조직·직급
조회 방식실시간 API마감 시점 스냅샷 1회
낡아도 되나된다안 된다. 정산 오류로 이어진다
임직원 장애 시기능 하나 실패스냅샷 확보 후라면 영향 없음
계약은 임직원으로 보내지 않는다

계약에는 연봉과 수당 조건이 들어 있다. 임직원 서비스로 옮기면 팩스·메일 서비스가 접근 가능한 범위 안에 급여 정보가 들어온다. 지금 읽지 않아도 경로가 열려 있는 것 자체가 문제다. 임직원은 누가 있는가를 답하고, 코어는 얼마를 받는가를 답한다.

기준 · 날짜 설계

시간축이 둘이어야 소급이 표현된다

발령에 날짜를 하나만 두면 3월 1일부로 승진, 5월 10일에 등록이라는 사실을 기록할 수 없다. 발효일만 있으면 5월에 등록했다는 사실이 사라지고, 등록일만 있으면 3월부터 적용된다는 사실이 사라진다.

발효일
3.1 승진 적용 시작
등록일
5.10 시스템 입력

두 날짜 사이에 3월·4월 급여가 이미 마감돼 있다. 그 간격이 곧 재계산 대상 기간이다. 축이 하나면 이 간격을 계산할 수 없고, 소급 정산 대상을 시스템이 판정하지 못한다.

테이블은 셋으로 나눈다

-- 본체: 거의 바뀌지 않는 것만 CREATE TABLE employee ( id bigint PRIMARY KEY, tenant_id bigint NOT NULL, employee_no varchar NOT NULL, name varchar NOT NULL, keycloak_sub uuid UNIQUE ); -- 재직 이력: 입사 퇴사 휴직 복직 CREATE TABLE employment_history ( employee_id bigint NOT NULL, status varchar NOT NULL, -- 재직 휴직 퇴직 effective_from date NOT NULL, effective_to date, registered_at timestamptz NOT NULL, reason varchar ); -- 발령 이력: 조직 직급 직책 CREATE TABLE assignment_history ( employee_id bigint NOT NULL, dept_id bigint, position varchar, effective_from date NOT NULL, effective_to date, registered_at timestamptz NOT NULL );

재직과 발령을 한 테이블에 합치지 않는 이유는 소비자가 다르기 때문이다. 4대보험은 자격 취득·상실만 보고, 인건비 배부는 발령만 본다.

휴직은 날짜로 표현되지 않는다

육아휴직 중에는 급여를 지급하지 않고 4대보험은 납부유예된다. 재직도 퇴사도 아닌 제3의 상태다. 입사일과 퇴사일 두 컬럼만으로는 이 기간을 표현할 수 없고, 휴직자에게 급여가 계산되는 사고로 이어진다. 재직 이력을 상태 이력으로 만들어야 하는 실무적 이유가 이것이다.

기준 · 기준일 정책

도메인마다 보는 날짜가 다르다

이력이 있어도 어느 날짜로 뽑느냐가 정해져 있지 않으면 매번 다른 답이 나온다. 특히 4대보험은 급여와 기준이 달라서, 명시하지 않으면 공단 신고분과 사내 계산이 어긋난다.

용도기준일어긋나면
급여 대상자지급 기준일 재직 여부중도 입퇴사자 일할 계산이 빠진다
부서별 인건비월말 소속 또는 발령일 안분부서 이동자 인건비가 이중 계상된다
4대보험자격 취득일 · 상실일공단 신고분과 사내 계산이 불일치한다
근태 집계근무일별 소속이동 전후 근태가 한 부서로 몰린다

이걸 값 객체로 명시하고 스냅샷에 함께 저장해라. 나중에 이 급여가 왜 이렇게 나왔나라는 질문에 답할 유일한 근거가 된다.

public record PayrollBasis( YearMonth period, LocalDate employmentAsOf, // 재직 판정 LocalDate organizationAsOf, // 조직 귀속 LocalDate insuranceAsOf // 보험 자격 ) {}

실행 · PostgreSQL 공략점

이력을 쌓는 비용보다 잘못 읽는 비용이 크다

시점 조회를 붙인다고 데이터가 늘지는 않는다. 데이터를 늘리는 건 이력 테이블 자체고, asOf는 이미 쌓인 이력을 읽는 방법일 뿐이다. 실제 위험은 용량이 아니라 인덱스가 안 먹는 쿼리 패턴과 겹쳐 들어간 이력 행 쪽에 있다.

아래 다섯은 효과가 큰 순서로 정렬했다. 앞의 셋은 스키마 수정 수준이고, 뒤의 둘은 설계 결정이다.

01
종료일을 NULL 대신 infinity로
막는 것 · 옵티마이저가 인덱스를 포기하는 현상

종료일이 NULL이면 조건이 effective_to IS NULL OR effective_to > $2 형태가 된다. OR 분기가 들어가는 순간 범위 인덱스를 제대로 못 탄다. 열린 구간을 무한대 날짜로 표현하면 조건이 단순한 범위 비교로 정리된다.

effective_to date NOT NULL DEFAULT 'infinity'
02
daterange 생성 컬럼과 GiST 인덱스
막는 것 · 범위 조건 두 개를 B-tree로 훑는 비용

시작일과 종료일을 각각 비교하는 대신 범위 타입 하나로 묶는다. 포함 연산자 @> 하나로 조건이 끝나고 인덱스가 그대로 탄다. 생성 컬럼이라 애플리케이션이 따로 채울 필요가 없다.

ALTER TABLE assignment_history ADD COLUMN valid_period daterange GENERATED ALWAYS AS (daterange(effective_from, effective_to, '[)')) STORED; CREATE INDEX idx_assignment_asof ON assignment_history USING gist (tenant_id, valid_period, employee_id); -- 조회는 이 한 줄로 끝난다 SELECT * FROM assignment_history WHERE tenant_id = $1 AND valid_period @> $2::date;
03
겹침 방지를 DB 제약으로 내린다
막는 것 · 같은 사람에게 기간이 겹치는 발령 두 건

겹친 이력이 들어가면 시점 조회가 두 행을 반환하고, 급여 계산이 어느 쪽을 쓸지 비결정적이 된다. 발견도 늦다 — 소급 재계산을 돌려보고 나서야 드러난다.

정합성 대책 중 비용 대비 효과가 가장 크다. 애플리케이션 검증은 동시 요청에 뚫리지만 이 제약은 뚫리지 않는다.

ALTER TABLE assignment_history ADD CONSTRAINT no_overlap EXCLUDE USING gist (employee_id WITH =, valid_period WITH &&);
04
마감 조회는 조인 두 번으로 끝낸다
막는 것 · 대상자 수만큼 반복되는 단건 조회

재직 이력과 발령 이력을 각각 한 번씩만 조인한다. 5000명이라도 인덱스를 타면 수십 밀리초 수준이고, 마감은 월 1회이므로 이 정도면 성능 논의 대상이 아니다.

SELECT e.employee_no, e.name, a.dept_id, a.position, h.status FROM employee e JOIN employment_history h ON h.employee_id = e.id AND h.valid_period @> $2::date LEFT JOIN assignment_history a ON a.employee_id = e.id AND a.valid_period @> $2::date WHERE e.tenant_id = $1 AND h.status IN ('재직', '휴직');

주의할 건 쿼리가 아니라 응답 크기다. 페이징하되 앞서 정리한 건수 대조를 반드시 함께 걸어라 — 부분 확보를 잡는 유일한 수단이다.

05
급여 결과를 덮어쓰지 않는다
막는 것 · 소급 정산 후 신고분 근거 소실

재계산할 때 기존 결과를 갱신하면 원천징수영수증과 4대보험 신고분이 어느 버전 기준이었는지 추적할 수 없게 된다. 감사 요건이라 선택 사항이 아니다.

CREATE TABLE payroll.payroll_result ( period date, employee_no varchar, revision int, -- 1, 2, 3... amount numeric, basis_as_of date, calculated_at timestamptz, PRIMARY KEY (period, employee_no, revision) );

여기가 실제로 데이터가 늘어나는 지점이다. 다만 소급이 발생하는 비율이 낮아 실질 증가는 크지 않다.

데이터량 실측 · 임직원 10만 명, 5년 누적

테이블누적 행증가 근거
재직 이력약 30만1인당 입사·휴복직·퇴사 3건
발령 이력약 100만1인당 연 1~3건
급여 결과약 600만월 1건 + 소급 리비전
근태 원천약 2.5억1인당 1일 2건 × 250일

이력 테이블 전체를 합쳐도 근태 원천의 1% 미만이다. 발령 이력은 사람 수가 아니라 사건 수에 비례하고, 인사 발령은 연 단위로 몇 건뿐이라 애초에 커질 수 없는 구조다. 용량을 이유로 시점 조회를 포기할 근거는 없다.

마이그레이션 순서 주의

기존 종료일이 NULL 허용이면 infinity로 바꾸는 게 먼저다. 그리고 겹침 제약은 마지막에 건다 — 기존 데이터에 이미 겹친 행이 있으면 제약 생성 자체가 실패한다. 검사 쿼리를 먼저 돌려 겹친 구간을 정리한 뒤 제약을 거는 순서여야 한다.

근거 · 데이터 배치

DB는 셋, 스키마는 일곱

접근 주체 employeehistorycontractattendance payrollinsuranceraw_punch
팩스 · 메일 R*——— ———
임직원 서비스 RWRW—— ———
근태 수집 ———— ——RW
코어 · 웹 R*—RWR RR—
코어 · 배치 R*R*RRW RWRWR†

* DB 직접 접근이 아니라 임직원 서비스 API 경유.  † 원본이 아니라 읽기 리플리카.

DB-0에 직접 붙는 건 임직원 서비스뿐이다. 코어도 팩스도 API를 통해서만 읽는다. 여기서 DB 공유를 허용하면 분산 모놀리스가 되고, 임직원 스키마를 바꿀 때마다 전부 같이 배포해야 한다.

임직원 서비스가 반드시 제공해야 할 것

  • 시점 조회. GET /employees?asOf=2026-03-31&tenantId=123 — 발령 이력이 있어도 API가 현재 상태만 주면 이력은 쓰이지 않는다.
  • 벌크 조회. 500명 마감에 500번 호출은 불가. 한 요청에 대상자 전체가 나와야 한다.
  • 소급 발령 통보. registered_at이 effective_from보다 늦은 등록이 발생하면 이벤트로 알린다.

기준 · 소급 처리

마감된 급여를 시스템이 바꾸지 않는다

소급 발령이 등록되면 영향받는 마감 기간을 판정해 재계산 대상 큐에 넣기만 한다. 자동 반영하지 마라. 급여는 담당자 승인 없이 숫자가 바뀌면 안 되는 도메인이다.

// 임직원 서비스 → 코어. 실시간 경로는 이것 하나뿐이다 AssignmentBackdated(employeeId, effectiveFrom, registeredAt) // 코어: 영향 기간 판정 후 큐 적재 affected = payroll.findClosedPeriodsAfter(effectiveFrom); affected.forEach(p -> retroQueue.enqueue(p, employeeId));

나머지는 전부 마감 시점 스냅샷 조회로 끝난다. 임직원과 코어 사이에 상시 동기화가 필요 없다는 뜻이고, 이것이 두 서비스를 느슨하게 유지하는 핵심이다.

근거 · 도입 판정

넣지 않을 것을 먼저 정한다

불필요
사가 패턴

근태 → 급여 → 보험은 단방향이고 급여가 근태 상태를 바꾸지 않는다. 소급 정산은 보상 트랜잭션이 아니라 업무 로직이다. 임직원이 분리돼도 이 판단은 유지된다 — 임직원 → 코어 역시 단방향이다.

불필요
카프카

코어 안 소비자는 전부 같은 JVM에 있다. 임직원 → 코어 통보도 이벤트 하나뿐이라 PGMQ로 충분하다. 프로세스 밖으로 나갈 이벤트가 늘면 그때 @Externalized로 경로가 열린다.

유지
PGMQ

근태 수집 → 코어, 임직원 → 코어 두 구간을 맡는다. 같은 Postgres 안이면 소비와 적재가 한 트랜잭션에 묶여 별도 아웃박스 테이블이 필요 없다.

유지
Keycloak · API 게이트웨이

인증 주체와 진입점을 맡는다. 도메인 서비스가 아니라 인프라 컴포넌트다. 게이트웨이가 여러 서비스 응답을 조합하기 시작하면 그때부터 네 번째 서비스가 된다.

도입
Event Publication Registry

코어 안 체인의 신뢰성, 그리고 Keycloak 계정 생성처럼 외부 호출이 섞인 단계의 재시도를 맡는다. 입사 처리는 커밋되고 계정 생성 실패만 미완료로 남아 재시도된다.

한계

이 구조가 보장하지 않는 것
